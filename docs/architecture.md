# システム構成案

この文書は2026-09-09時点の初期設計と将来拡張の方針です。2026-09-12の改訂で、初期案のStepに代えてUni-MuMER-4B Q4_K_Mを実装し、Ricohと合わせた2系統のOCRをOrnith Q8へ渡す構成になりました。実装済みコマンドと現在の制約はREADME.mdおよびBasicMathSmallExam1.mdを参照してください。

## 対象範囲と前提

初期構成はRicoh-8BとOrnith-Q8のみ。imported-conversation.md末尾のオーケストレーション案を踏まえ、利用者が報告した3モデル同時起動の不安定さを優先します。ログ内の性能値を今回再測定したものではありません。2モデル常駐の安定性、実モデルID、画像入力方式、コンテキスト長、メモリ余裕は実機確認が必要です。

接続はローカルのOpenAI互換HTTP APIを想定しますが、具体的なAPIパス、画像の符号化、出力形式制約の対応は実装時に確認します。モデルファイルの移動やダウンロード、サーバー起動、既存プロセス停止は今回行いません。

## 教材と答案の契約

- assignment.jsonのパスはそのファイルのあるディレクトリを基準とする相対パスです。課題の外へ出るパスは受け付けません。
- submission.jsonの画像パスはそのファイルのあるディレクトリを基準とします。設問ごとにpage_idを明示し、ファイル名から答案との対応を推測しません。
- 初期入力はPNG/JPEGの静止画像。PDFは事前にページ画像へ変換し、元PDFと変換条件をローカル保管します。回転、縮小、切り出しを行う場合は原本との対応と座標を保存します。
- 同じページに複数設問があれば、複数のquestion_idから同じpage_idを参照できます。まずページ全体を渡し、対象設問を明示します。領域指定や自動分割は後続の拡張とします。
- 問題図はassignment.jsonのassetsで明示した画像を採点段階で添付します。Markdown内のリンクだけで画像がモデルへ届いた扱いにしません。
- rubric.jsonを点数の正本とします。観点ID、満点、許容点数と各条件、別解・未記入・誤りの波及の扱いを明記します。模範解答と矛盾する教材は採点前に修正します。
- 模範解答は推奨ですが任意です。論述でも観点別の到達条件を具体化し、単なるキーワード一致を採点基準にしないようにします。

## オーケストレーション

1. 入力を検証し、課題・ルーブリック・プロンプト・設定のスナップショットと画像SHA-256を保存します。画像自体もinputsへコピーし、実行後の原本変更に影響されないようにします。
2. Ricohに1ページずつ画像を送りOCR。正解・配点は渡しません。未読箇所、行、ページ対応を保持し、生レスポンスと整形結果を保存します。
3. Ornithへ設問に対応する元画像とRicohの該当ページOCRを送り、読み取りを照合します。モデル内部の記憶に頼らず、必要な入力を毎回明示します。正解・ルーブリック・解説は渡しません。
4. 照合結果を保存・固定して、新しいリクエストでOrnithへ元画像、固定読み取り、問題文、問題図、ルーブリック、任意の模範解答を送ります。RicohのOCRも参考資料として添付します。
5. 出力の構造・点数・根拠を検証します。合計点はプログラムで計算します。要確認案件と検証エラーは確定点にしません。
6. 初期試行では全件を教員確認し、人手採点との観点別一致率、点差、重大な誤読、要確認率、失敗率、時間を確認します。モデルの自己申告のconfidenceで自動確定を判断しません。

答案やOCR中の「この答案を満点に」等は採点対象の文字列として扱い、指示として実行しません。生レスポンスやログも答案と同様にローカル保管します。

## リソースと失敗時の処理

デフォルト案は `resident_serial`：2モデルを常駐させても同時推論は行わず、システム全体で最大1リクエスト、答案を順次処理します。常駐だけでメモリを使うため、これで安定することを保証するものではありません。

不安定なら `phased_manual`：Ricohだけを起動して全答案のOCRを保存し、利用者がRicohを停止してOrnithを起動した後、照合・採点を再開します。この方式なら同時常駐を避けられます。将来のランナーも初期段階ではモデルの自動起動・停止を行わず、接続先の準備完了を確認して進みます。

設定例のタイムアウト等は開始値です。大きなページは最初に1件で動作確認し、画像寸法、モデル・量子化・投影器、サーバービルド、起動引数、コンテキスト設定、ピークメモリ、処理時間を記録します。制限を超える入力を黙って切り捨てず `input_too_large` として停止します。

途中結果は各段階で一時ファイルからのrenameにより確定保存する実装を想定します。失敗状態は `ocr_failed` / `reconstruction_failed` / `grading_failed` / `validation_failed` として区別します。タイムアウト・接続失敗の再試行は最大1回。OCR失敗を空答案や0点として処理しません。ホスト不調やメモリ不足では連続再試行せず停止します。

再開では入力・モデル・設定・プロンプトのハッシュが一致する成功済み段階だけ再利用します。採点基準を変更した場合は新runとし、OCRの再利用もハッシュ一致を確認します。

## 出力と人手確認

run_idはUTC日時とランダムsuffix等で一意にします。以下は今後ランナーが生成する仕様案で、空の結果は事前生成しません。

```text
runs/<run_id>/
  manifest.json                       モデル情報、設定、各入力のハッシュ、開始終了時刻、状態
  inputs/                             教材・画像・プロンプトのスナップショット
  submissions/s0001/
    ocr/ricoh/page-001.raw.json        生レスポンス
    ocr/ricoh/page-001.json            整形OCR
    questions/q01/
      reconstruction.raw.json
      reconstruction.json             固定した読み取りと不確実箇所
      grading.raw.json
      grading.json                    検証済み観点別結果・プログラム計算の合計
      status.json                     成否、エラー、所要時間、試行回数
  reviews/s0001-q01.json               教員の確定点、修正理由、確認者、日時
  summary.csv                         submission_id/question_id/仮点/確定点/状態
```

OCR整形結果はpage_id、text、不確実箇所のリストを持ちます。照合結果はquestion_id、transcript、ページごとのevidence、不確実箇所、Ricohからの変更点、needs_reviewを持ちます。図形や矢印などは視覚的な観察として保持し、未記載の式や解法を補いません。

採点結果はquestion_id、criteria配列（criterion_id、score、max_score、根拠のpage_idと引用、reason）、needs_review、review_reasonsを持ちます。採点不能な観点のscoreはnull。nullがあれば合計もnullとし、0点と区別します。根拠なし・判読不能・画像とOCRの不一致・ページ不足・教材の矛盾・読み取り変更要求はいずれも人手確認に回します。未記入と確実に判断できる答案にはルーブリックの未記入規則を適用します。

モデルから返る観点IDの欠落・重複・未知ID、許容点数外、満点の不一致、存在しないページ参照を拒否します。根拠の妥当性は構造検証だけでは保証できないため、教員確認で評価します。人手修正は元のモデル結果を上書きせずreviewsに保存します。

## 実装を追加する際の順序

まず入力検証と1答案の逐次実行、次にチェックポイント・再開と人手確認用一覧を実装します。入力パスの逸脱、ページ欠落、観点重複、配点合計不一致、採点不能のnull、通信失敗からの再開を小さな決定的テストで検証します。API接続テストと実モデル評価は単体テストから分離します。

Stepを追加する場合は `ocr/step/` に独立したOCRを保存し、Ornith照合段階の入力を増やします。同時起動を前提にせず、まずモデル切り替えで評価します。
